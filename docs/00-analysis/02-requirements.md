## 一、产品定位（一句话）

把四个已独立上线并验证过的学术原型（**ScholarMatrix / 星门 / PAT-HOT / 预职**），从"42 个工具挤在一个单页"解耦重构为 **18 个职责单一、各自拥有独立二级域名与独立持久化台账的微站**，用统一账号、统一 AI 副驾驶、跨站虫洞协议串成覆盖「学业 → 科研 → 生涯」的 7 站闭环。

**服务对象**：高校拔尖创新人才（本科生科研为主）。
**核心叙事**：把"科研过程数据"变成"可申报的综测加分 + 可验真的求职简历"——即**学术数字资产化**。

## 二、7 站生涯闭环

7 条轨道对应学生从入学到就业的完整链路。轨道编号在花名册里以 `orbit` 字段呈现为**分组键**（4 组），`orbitName` 才是逐站名称：

| 站 ID（契约枚举） | 轨道 | 中文名 | 分组键 `orbit` | 承载微站数 | 在该站发生的事 |
| :--- | :--- | :--- | :--- | ---: | :--- |
| `study` | 轨道 1 | 学阶 | `1-2` | 1 | GPA 推子配重、选课博弈 |
| `spark` | 轨道 2 | 星火 | `1-2` | 2 | 双创组队、经费合规 |
| `pat_hot` | 轨道 3 | 情报 | `3-4` | 2 | 24h 前沿监听、文献引文网络 |
| `xingmen` | 轨道 4 | 星门 | `3-4` | 3 | 导师匹配、套磁、进组台账 |
| `workshop` | 轨道 5 | 学术星轨工坊 | `5` | 7 | 科研攻坚主力（对比/拟合/写作/合规） |
| `cloud_balance` | 轨道 6 | 云衡 | `6-7` | 1 | 综测加分核算 |
| `pre_job` | 轨道 7 | 预职 | `6-7` | 2 | 证据简历、生涯决策树 |

**闭环逻辑**（README L5 与 HTML L12 一致）：
```
学阶(绩点) → 星火(立项) → 情报(追前沿) → 星门(进组) → 工坊(做科研) → 云衡(变现综测) → 预职(变现offer)
                  ↑                                                          │
                  └──────────────── 过程数据反向沉淀 ←───────────────────────┘
```

> ⚠️ **数据结构上的一个坑**：轨道有 7 个，但花名册的 `orbit` 字段只有 **4 个值**（`1-2` / `3-4` / `5` / `6-7`）。也就是说"轨道分组"与"7 站枚举"是两套粒度。
>
> 后果：**Tab 3 的 5 个筛选按钮实际只能筛出 4 组结果**（`all` + 4 组）。轨道 1 与轨道 2 在 UI 上永远合并展示，轨道 3 与 4 同理，6 与 7 同理。若产品要求"按 7 站逐站筛选"，当前数据结构不支持，需给花名册补 `station` 字段（值为 7 个枚举之一）。
>
> `specs/contracts/*.schema.json` 里的 `orbit_station` 用的是 7 站枚举，`microsites.json` 用的是 4 组 —— **两套粒度并存且没有映射表**。Stage 1 应补 `station` 字段打通。

## 四、五大锁定架构决策（Q1–Q5）

这五项在 HTML 中均标注"已锁定"，是经过推演后的结论，**不在 Stage 1 重新讨论**。出处见 HTML L370–380（`masterSpecPre` 的 §1 五大核心架构公理）。

### Q1 · 产品形态 —— 18+N 群岛式独立微站

> 原文（L371）："彻底废除臃肿的单页 42 工具堆砌，将现存 4 大线上实机原型……解耦重构为 **18 个职责单一、拥有独立二级域名 (`*.matrixos.edu`) 与独立持久化项目台账的精品微站**。"

| 维度 | 要求 |
| :--- | :--- |
| 站点数 | 18 官方旗舰站（固定） + N 实验室自研站（开放） |
| 域名 | 每站一个 `<app_id>.matrixos.edu` 二级域名 |
| 职责 | 单一职责，不再有"什么都能干"的页面 |
| 持久化 | 每站独立台账（`ledger` 字段已定义） |
| 部署 | 独立部署（"18 个独立部署、单一职责的微站应用"） |

**隐含的硬约束**：18 个独立部署 + 共享鉴权 + 跨站拖拽，等价于 18 个独立 origin。这直接决定了必须走**子域名**而非子路径（见 `04-tech-decisions.md` 的 ADR-002）。

### Q2 · 账号与数据底座 —— MatrixID 全息数字孪生

> 原文（L372）："全域共享唯一 `MatrixID` (OAuth2 + JWT) 与底层统一 `DigitalTwinAssetGraph`（PostgreSQL + pgvector 向量库 + 端侧 IndexedDB 隐私保险箱）。**严禁让用户在子网站之间手动导出/导入文件。**"

| 组件 | 技术 | 职责 |
| :--- | :--- | :--- |
| `MatrixID` | OAuth2 + JWT | 单点登录，全域唯一用户标识 |
| `DigitalTwinAssetGraph` | PostgreSQL | 结构化资产图谱（论文/实验/软著/竞赛） |
| 向量检索 | pgvector | 语义检索、导师匹配度对齐 |
| 端侧隐私仓 | IndexedDB（加密） | 课题组未发表数据隔离，零外泄 |

**"严禁手动导出/导入"是产品级红线**——它否定了"下载 JSON 再上传到下一个站"的低成本实现路径，强制要求虫洞投送必须是程序化、免文件中转的。

### Q3 · AI 交互范式 —— 全局常驻 Copilot + 跨站虫洞

> 原文（L374）："18 个微站共享唯一「全局常驻 AI 副驾驶 (Global Copilot)」，支持跨站上下文记忆；在任意微站按住数据卡片拖拽，鼠标周围即刻张开全息**「Agent 跨站虫洞环 (`WormholeDropRing`)」**，松手即可携带结构化参数与 PDF 证据锚点空间翻转至目标微站。"

三个能力要求：

1. **全局常驻（唯一实例）**：不是每站一个 bot，而是共享一个带跨站上下文的 Copilot。总控台形态是"底部声波脉冲底座"，进入独立微站后"坍缩为右下角呼吸能量球"（L378）。
2. **跨站上下文记忆**：HTML 演示文案是"当前携带 3 篇顶刊对比矩阵 + 1 组钙钛矿双指数拟合曲线"（L243）。
3. **虫洞拖拽**：按住卡片 → 张开环 → 松手投送。**这是 Q3 的核心，也是当前设计稿唯一完全没实现的部分。**

**虫洞数据契约**（HTML L381–419 / `specs/contracts/wormhole-envelope.schema.json`）：

```jsonc
{
  "required": ["trace_id", "matrix_uid", "source_app", "target_app", "payload_type", "payload"],
  "payload_type": [                              // 5 种载荷，枚举锁定
    "paper_doi_bundle",
    "comparison_matrix_row",
    "curve_fit_parameters",
    "mentor_match_card",
    "verified_cv_evidence"
  ],
  "payload": {
    "required": ["data", "evidence_anchors"],     // 证据锚点必填 —— 防幻觉红线
    "evidence_anchors[]": {
      "required": ["source_doi_or_url", "verification_level"],
      "verification_level": ["Level_A_Verified", "Level_B_Preprint", "Retracted_Warning"]
    }
  }
}
```

> **`evidence_anchors` 必填且 `minItems: 1`**（`wormhole-envelope.schema.json` L46）。这是整个架构最有价值的设计决策：**任何跨站流动的数据都必须自带可回溯的证据锚点**（DOI + PDF 页码 + bbox 坐标），从契约层杜绝大模型幻觉。`scripts/validate-specs.mjs` 的 `[4/5]` 步骤专门校验这一条，称为"合规红线"。

### Q4 · 主视觉与导航 —— 星轨引力场 + 精密仪器双态合体

> 原文（L376–378）："**双态合体总控台 (`orbital.matrixos.edu`)**：左侧 32% 为 2.5D 交互式 7 轨星图（环绕 18+ 动态实况微缩胶囊），右侧 68% 为折射挂载的 2~3 台数字精密科研仪器面板，底部常驻 AI Copilot 声波脉冲底座。**100% 独立微站专精态 (`*.matrixos.edu`)**：点击 `[↗ 全屏独立打开]`，即刻进入该微站的 100% 独立定制 UI，底部声波条自动坍缩为右下角呼吸能量球。"

| 态 | 布局 | 关键行为 |
| :--- | :--- | :--- |
| **总控态**（合体） | 左 32% 星轨 + 右 68% 仪器架 + 底声波坞 | 同屏挂载 2~3 台仪器；点胶囊切换组合 |

### 7.1 B/C 双轮造血模型（Tab 4 仿真器）

三个滑块变量 + 三条营收/成本公式（`runFinanceSim`, L1759–1781）：

| 输入 | 滑块范围 | 默认值 |
| :--- | :--- | :--- |

| C 端 Pro 算力包订阅率（¥10/月） | 1.0% – 8.0%，step 0.5 | 3.0% |
| 签约重点实验室 SOP 私有部署（¥1.5 万/个） | 0 – 10，step 1 | 2 |

```
年总成本  = 15000 + 6000 + round(MAU × 1.76)
C 端营收  = round(MAU × 订阅率%) × 10 × 12
B 端营收  = 实验室数 × 15000
年净现金流 = C端 + B端 − 年总成本
```

默认值下：成本 ¥38,600 / 营收 ¥66,000 / 净现金 **+¥27,400**（与页面静态文案 L1101–1109 一致）。

## 九、需求侧的开放问题（Bundle 未覆盖）

以下项目在 Bundle 中**完全没有定义**，不是"实现难度问题"而是"规格缺失问题"，必须在 Stage 1 用 ADR 补齐：

| # | 缺口 | 影响 |
| :-- | :--- | :--- |
| R1 | **7 站枚举 ↔ 4 组 `orbit` 的映射规则** | 无法按站筛选；契约与花名册粒度不一致 |

| R3 | **`DigitalTwinAssetGraph` 的实体/关系模型** | 只说"PostgreSQL + pgvector"，无任何表结构、ER 图、资产类型定义 |
| R4 | **18 站之间的虫洞可达矩阵** | 5 种 `payload_type` 与 18 站的 `accepts`/`emits` 关系未定义。理论上 18×18×5 的可达组合里，哪些合法完全空白 |
| R5 | **`ledger`（持久化台账）的数据结构** | 18 条 `ledger` 只有中文描述名，无字段定义 |

| R9 | **"500+ 种子用户"的获取方式** | 只有目标数字，无试点校合作模式 |
| R10 | **`@matrixos/sdk` 的实际 API 签名** | 只有 3 个方法名，无参数、无返回值、无错误码 |
