## 0. 使用说明

### 概率 / 影响评级

| 等级 | 概率 | 影响 |
| :--- | :--- | :--- |
| **高 (H)** | > 60% | 导致阶段门禁不通过，或工期延误 > 1 个月，或核心承诺失效 |
| **中 (M)** | 30%–60% | 导致部分功能降级，或工期延误 2 周–1 个月 |
| **低 (L)** | < 30% | 局部返工，影响可控在 2 周内 |

**风险值 = 概率 × 影响**，取值 H/M/L，用于排序。`H×H` 为最高优先级。

## 2. 技术风险 (T)

### R-T01 · 42+ 工具解耦工作量被严重低估 【H × H】

**描述：** ScholarMatrix 的 42+ 工具在原型中可能深度耦合（共享全局状态、隐式依赖 UI、硬编码路径）。无状态化改造不是「包一层 API」，而是要把交织的逻辑重新切开，工作量可能是估算的 2–3 倍。

**触发信号：** `S1-07e` 的耦合度扫描中，「难」级别工具占比 > 30%（预期 20%）。

**缓解措施：**
1. `S1-07e` 在第 2 周即给出分级，**先扫描再承诺**，不拍脑袋定 20 个；
2. S1 只承诺 P0 的 20 个工具，且**耦合度为「难」的工具一律不进 S1**；
3. 若扫描后发现「易 + 中」不足 20 个，立即缩减 S1 的 D1.5 范围至实际可解耦数量，并把剩余推到 S3；
4. 工具池采用「适配器模式」：难解耦的工具先包一层同步适配器（内部串行调用旧逻辑），保证接口统一，内部债留待 S3 还。

**责任人：** DS（执行）+ TL（范围裁决）
**关联任务：** `S1-07e`、`S1-14`

---

### R-T02 · 虫洞契约反复变更导致 18 站返工 【H × H】

**描述：** Wormhole envelope 是 18 站 + 第三方站的共同依赖。若在 S2/S3 发现设计缺陷（如 `payload_type` 枚举不够用、`evidence_anchors` 结构不适配某类证据），修改会触发全面返工。

**触发信号：** S1 契约冻结后，出现第 2 次以上的字段语义变更请求。

**缓解措施：**
1. **S1 第 2 周冻结 v1.0**，文档化并全员评审（不只是 TL 看）；
2. 采用 ADR-10 的「只增不改 + 版本化」策略，v1 内只允许新增可选字段；
3. 契约设计时为已知的 6 类 `payload_type` 各写一个真实样例（取自四个原型的实际数据），用真实数据验证结构；
4. 预留 `payload.data` 为自由 object，站点自定义结构不受契约约束——这是最重要的解耦点。

**责任人：** TL
**关联任务：** `S1-02`、`S1-04`；ADR-10

---

### R-T03 · iframe 多实例性能崩塌 【H × H】

**描述：** hub 同屏挂载 3 个 Next.js 应用 = 3 份 React 运行时 + 3 个 hydration + 3 份 SDK。在低端笔记本上可能内存占用 > 1GB、主线程长任务频发、星轨动画掉帧。这会直接摧毁「双态合体」这个核心视觉卖点。

**触发信号：** `S2-01e` 探针显示 3 iframe 下星轨帧率 < 45fps，或内存 > 800MB，或长任务 > 100ms。

**缓解措施：**
1. `S2-01e` 在 S2 第 2 周做，**早发现早决策**，不留到后期；
2. 预设降级方案：**1 个全量 iframe + 2 个静态快照缩略图**（视觉上仍「同屏 3 台仪器」，实际只有 1 台活的）。这个方案在 S2-01e 之前就要在设计上留好后路（快照组件）；
3. iframe 采用「懒加载 + 可见才 hydrate」：右侧仪器架未激活的面板不加载；
4. 星轨动画用 CSS transform + `will-change` 而非 JS 驱动，减轻主线程；
5. 低性能设备检测（`navigator.hardwareConcurrency` / 帧率采样）后自动降级为「单仪器模式」。

**责任人：** FE + TL
**关联任务：** `S2-01e`、`S2-02`、`S2-03`；ADR-08

---

### R-T04 · 第三方 Cookie 限制导致 iframe 内登录失效 【H × M】

**描述：** Safari ITP 与 Chrome 的第三方 Cookie 限制会让 iframe 内的微站收不到 `mx_at`，导致「hub 里能看到仪器面板，但一点就要求重新登录」。这是真实存在、且会随时间恶化的平台限制。

**触发信号：** S2 联调时在 Safari 或 Chrome 隐身模式下 iframe 内调用 API 返回 401。

**缓解措施：**
1. `S2-07` 的 `mx_idt` 交换机制**是必做项不是优化项**，S2 第 1 周就实现并验证；
2. 双路径设计：非 iframe 走 Cookie，iframe 走 `mx_idt`，SDK 内部统一封装，开发者无感；
3. 测试矩阵必须包含：Chrome 正常 / Chrome 无痕 / Safari / 禁用第三方 Cookie 四种环境；
4. 兜底：若 `mx_idt` 交换也失败，iframe 内展示「点击此处在新标签页打开」（降级但不阻断）。

**责任人：** BE2 + BE1
**关联任务：** `S2-07`、`S1-09`；ADR-03

---

### R-T05 · 单用户年均 API 成本 < ¥1.5 无法达成 【H × M】

**描述：** ¥1.5/年 意味着约 2000 token/天。若用户行为集中在 Pro 类任务（长文本对比、综述生成），成本会远超预期。这个目标在蓝图里是**承诺**，不是期望。

**触发信号：** `S2-11` 的 100 用户 1 月回放测试折算年成本 > ¥1.5。

**缓解措施：**
1. 三层控制（ADR-06）：路由准确率 ≥ 95% + 日成本熔断 + 结果缓存；
2. 结果缓存针对「多用户查同一篇热门论文」场景，试点校同专业重叠度高，命中率应显著；
3. 若实测超标，**按优先级依次启用**：① 提高缓存命中（相似请求合并）；② 给 Pro 设每日配额；③ 长文本任务改为「用户主动触发」而非自动；
4. **诚实处理**：若以上都不够，向项目负责人报告并请求重新设定成本目标，**不通过降低功能质量来凑数字**。

**责任人：** DS + TL
**关联任务：** `S2-10`、`S2-11`、`S2-12`、`S4-10`；ADR-06

---

### R-T06 · 向量检索在数据量增长后成为瓶颈 【M × M】

**描述：** pgvector 在千万级向量上性能显著落后于专用向量库。当前预估试点期 30 万向量、扩容期 300 万，尚在可承受范围，但若资产规模超预估会有问题。

**触发信号：** `asset_chunk` > 500 万行，或向量检索 P95 > 500ms 持续一周。

**缓解措施：**
1. 设定明确的扩容触发阈值（已写入 ADR-04），监控 `asset_chunk` 行数与检索 P95；
2. HNSW 参数按实际数据调优（`m` / `ef_construction` / `ef_search`）；
3. 冷热分离：老资产的向量可下沉到低成本存储，检索时先查热数据；
4. 预留切换到 Qdrant 的迁移路径（`matrix-core` 内部把检索抽象为接口，不硬编码 SQL）。

**责任人：** BE2
**关联任务：** `S1-10`、`S1-11`；ADR-04

---

### R-T07 · 仪器组件（Canvas 示波器/声呐盘）工作量超估 【M × H】

**描述：** 「1 万点数据实时重绘 + 置信带 + 残差频谱 + 阻尼旋钮联动」不是画折线图，涉及 Canvas 性能优化、坐标系变换、插值算法。`S3-02` 的 15 pd 估时可能偏乐观。

**触发信号：** `S3-02` 消耗超过 20 pd 仍未达到 30fps 指标。

**缓解措施：**
1. 先做技术验证（spike）：用 1–2 天验证「1 万点 30fps」是否可达成，再定实现方案；
2. 性能优化手段：Canvas 双层（静态层 + 动态层）、离屏渲染、数据降采样（显示降采样但计算用全量）；
3. 若性能确实达不到，**降低视觉指标而不是砍功能**（如 1 万点降到 5 千点显示，或 30fps 降到 24fps）；
4. 降级：低性能设备关闭光晕/残差动画。

**责任人：** FE
**关联任务：** `S3-02`、`S3-MS11`；ADR-07

---

### R-T08 · 端侧密钥丢失导致数据永久不可恢复 【M × H】

**描述：** 端侧隐私仓的密钥由用户 passphrase 派生，服务端不持有。用户忘记 passphrase = 未发表实验数据永久丢失。这会引发真实的用户投诉，甚至是学术损失。

**触发信号：** 出现第一例用户忘记 passphrase 的求助。

**缓解措施：**
1. UI 在设置 passphrase 时**强制**二次确认 + 明确警告「丢失不可恢复」；
2. 提供**加密备份导出**功能（用户自行保管加密文件）；
3. 提供可选的「恢复码」机制：生成一次性恢复码让用户抄写保存，用于重置 passphrase；
4. 写入用户协议（知情同意）。

**责任人：** BE1 + TL
**关联任务：** `S2-14`；ADR-05

---

### R-T09 · 契约漂移未被 CI 捕获 【M × M】

**描述：** 若 CI 的契约检查有漏洞（如只检查了部分 schema、或生成脚本可被绕过），会积累隐蔽的不一致，最终在联调时集中爆发。

**触发信号：** 联调阶段发现前后端字段名/类型不一致。

**缓解措施：**
1. `S1-04` 验收要求「故意破坏必须红」的实测证据；
2. 契约检查覆盖**全部** schema（Wormhole / manifest / AssetNode / Dispatch），不是抽样；
3. 生成物必须入库（`contracts/openapi/`），CI 比对工作区与生成结果；
4. 联调前做一次全量契约一致性审计。

**责任人：** TL
**关联任务：** `S1-04`、`S4-12`

---

### R-T10 · 离线降级路径遗漏导致白屏 【M × M】

**描述：** `matrix-core` 不可用时，若某微站没实现 L2 只读离线（ADR-09），用户看到的是白屏或无限 loading。18 个站里漏一个，就等于该场景下体验崩塌。

**触发信号：** 故障演练时发现某站未实现离线路径。

**缓解措施：**
1. 离线路径由 SDK 统一提供（`MatrixSDK` 内置缓存读写），微站不自己实现，降低遗漏概率；
2. 站点验收模板（`03-work-breakdown.md` S3-E2 的 12 项）中增补离线检查项；
3. S3 做一次**真实的 `matrix-core` 宕机演练**，逐站检查降级行为；
4. SDK 中把「未配置离线策略」做成默认可用的兜底，而非要求每个站显式配置。

**责任人：** BE1 + TL
**关联任务：** `S2-16`；ADR-09

---

### R-T11 · 旧数据无法迁移至 AssetGraph 【M × M】

**描述：** 四个原型的历史数据可能无 `matrix_uid`、无结构化证据锚点、无 DOI 关联，无法直接导入统一的资产图谱。强行迁移会产生大量脏数据。

**触发信号：** `S1-13` 迁移脚本的可识别率 < 70%。

**缓解措施：**
1. S1 只承诺**新数据**入图，旧数据迁移列为 P1 且允许降级；
2. 降级方案：只迁元数据（标题、时间、摘要），正文与文件留在原处，通过 URL 引用；
3. 无法迁移的记录产出明确清单，不静默丢弃；
4. 迁移脚本幂等，可反复执行。

**责任人：** DS
**关联任务：** `S1-13`

---

### R-T12 · 第三方实验室微站引入安全风险 【M × M】

**描述：** A5 开放插槽允许第三方代码接入。即使有 iframe 隔离，第三方站仍可能：伪造 `evidence_anchors`、超范围请求资产、在虫洞投送中注入恶意 payload。

**触发信号：** 第三方站的 manifest 声明了超出其真实能力的需求，或出现异常高频的资产访问。

**缓解措施：**
1. 第三方站使用 `mx_devkey`，scope 由 manifest 的 `accepts[]` 决定，**最小权限**；
2. 虫洞接收方必须校验 `verification_level`，来自第三方的载荷默认只接受 `Level_B_Preprint` 及以下，`Level_A_Verified` 需人工审核来源；
3. 第三方站的资产写入进独立 schema 命名空间，不污染官方资产；
4. 监控第三方站的调用频次与异常模式，超阈值自动限流。

**责任人：** BE2 + TL
**关联任务：** `S4-05`、`S4-06`、`S4-07`；ADR-08

## 3. 进度风险 (S)

### R-S01 · 18 站并行开发导致质量参差、验收失控 【H × H】

**描述：** 78 个 S3 任务里 18 个是微站交付，由 3 名全栈分摊。密集并行下，很容易出现「能跑就算完成」、站点之间体验不一致、验收标准被稀释。这是本项目最现实的进度+质量双重风险。

**触发信号：** 任一站在第一轮验收中通过率 < 80%（12 项模板）。

**缓解措施：**
1. **强制站点验收模板**（12 项，`03-work-breakdown.md` S3-E2），逐项打钩，缺一不算完成；
2. 18 站**分两批**交付（第 2 月 9 站、第 4 月 9 站），同批内按轨道分组，避免 18 个 PR 同时涌来；
3. 组件复用率纳入验收：每站必须使用 `instrument-ui` 对应仪器族，不自造轮子——这既是质量保障也是视觉一致性保障；
4. 指定 BE1 为「站点质量守门人」，负责验收而非开发；
5. 每站必须有 E2E 用例，无 E2E 的站不予验收。

**责任人：** TL + BE1
**关联任务：** S3-E2 全部 18 站

---

### R-S02 · 关键路径上的契约或鉴权延期引发连锁 【H × H】

**描述：** 关键路径为 `S1-02 → S1-08 → S1-11 → S1-15 → S2-07 → S2-05 → 核心微站 → S4-01 → S4-03 → S4-08`。其中任一环延期，后续全部顺延，且没有并行压缩空间。

**触发信号：** 关键路径上任一任务的实际进度落后计划 > 15%。

**缓解措施：**
1. 关键路径任务**只派给最可靠的人**，不派给新手练手；
2. 关键路径任务每周单独跟踪，不等阶段末复盘；
3. 前置任务的接口在开工前先定（如 `S1-02` 的 schema 先出草稿给 `S1-08` 用），允许「契约先行、实现跟上」；
4. 关键路径上有 15% 的缓冲（已含在阶段里程碑中）；
5. 若 `S1-08`（鉴权）确实延期，可采用**临时简化鉴权**（单一 JWT 无 scope 细分）先跑通链路，scope 细化后补——但要登记为技术债。

**责任人：** TL
**关联任务：** 见关键路径

---

### R-S03 · 试点高校对接延误导致 S3 空转 【H × M】

**描述：** S3 需要 3 所高校的物理/光电实验室配合（网络策略、CAS 对接、用户组织）。高校行政流程慢，若谈判在 S3 才开始，试点会大幅缩水或延期。

**触发信号：** S2 结束时仍未锁定 3 所高校的合作意向。

**缓解措施：**
1. **S2 期间就启动三校谈判**（不等到 S3），这是 roadmap 里明确要求的；
2. 每校配 1 名对接人，建立直接沟通渠道（而非走院系层层转达）；
3. 降低单校门槛：先做「1 个实验室、50 用户」的小规模验证，跑通后再扩；
4. 若某校确实卡住，用「2 校 + 线上用户」替代，保证 500 用户总量（用户来源可多样，不必全来自签约校）。

**责任人：** TL + 项目负责人
**关联任务：** `S3-19`

---

### R-S04 · 考试周/假期导致有效工时骤降 【H × M】

**描述：** 高校团队的真实约束：期末考试周（每学期约 2 周）、寒暑假（成员回家）、毕业季。12 个月工期里约有 3–4 个月是低效期。我的排期已含 40% 缓冲，但若低估会更糟。

**触发信号：** 某月实际完成任务量 < 计划的 60%。

**缓解措施：**
1. 排期时**主动避开**考试周安排关键路径任务；
2. 假期前把需要协作的任务做完，假期安排可独立完成的任务（如文档、软著材料、单站开发）；
3. 864 pd 估时对应 7.2 个月人力当量，对 12 个月工期留 40% 缓冲——这个缓冲不应被「反正有缓冲」的心态提前消耗；
4. 每月复盘实际吞吐量，动态调整后续排期。

**责任人：** TL
**关联任务：** 全局

---

### R-S05 · 软著审查周期赶不上结题 【M × H】

## 4. 资源风险 (R)

### R-R01 · 团队 6 人不足以支撑 18 站 + 3 服务 【H × H】

**描述：** 864 pd 对应 7.2 个月人力当量，6 人团队全年可用约 1440 pd（6 人 × 12 月 × 20 天）。表面有 40% 余量，但这 40% 要覆盖：Code Review、会议、答辩、运维、突发故障、人员流动。**实际可能刚好或不足。**

**触发信号：** 连续 2 个月实际吞吐 < 计划 70%。

**缓解措施：**
1. **优先级是唯一的护城河**：P0 60 个任务必须先完成，P2 的 2 个任务随时可砍；
2. 18 站中 P2 站点（`S3-MS02` spark、`S3-MS12` repro-check）可在资源不足时推迟到 S4 或 Backlog；
3. 组件库与脚手架是效率杠杆——`S1-15` 脚手架省下的时间会在 18 站开发中成倍返还，**这个投入不能省**；
4. 若确实不足，**缩减试点规模**（3 校 → 2 校）比降低 18 站质量更可取；
5. 明确不做的：BL-01~05 全部不进 v3 范围。

**责任人：** TL + 项目负责人
**关联任务：** 全局

## 5. 合规风险 (C)

### R-C01 · 学生个人信息与学术数据的合规处理 【H × H】

**描述：** 系统处理学号、成绩、GPA、导师沟通记录、未发表实验数据。这些涉及《个人信息保护法》与高校数据管理规定。若处理不当，可能面临合规审查甚至叫停。

**触发信号：** 试点校的信息安全部门提出审查要求。

**缓解措施：**
1. **数据最小化**：只收集完成功能所必需的数据，不做「先收了再说」；
2. **知情同意**：注册时明确告知数据用途、存储位置、共享范围，取得同意；
3. **端侧隔离**：未发表实验数据不上传（ADR-05），从架构上消除最大风险；
4. **权限最小化**：scope 细粒度（ADR-03），平台运维不可读业务正文；
5. **数据可导出可删除**：用户有权导出全部数据、有权注销并删除；
6. S3 试点前完成合规自查清单，必要时请学校法务/信息办审核。

**责任人：** TL + 项目负责人
**关联任务：** `S3-19`、`S4-13`

---

### R-C02 · 学术数据抓取（OpenAlex/arXiv/Crossref）的合规边界 【H × M】

**描述：** PAT-HOT 与导师图谱依赖对 OpenAlex、arXiv、Crossref、PubPeer 的抓取。若超出 API 条款（频率、范围、商业使用），可能被限流或封禁。

**触发信号：** 收到 API 提供方的限流警告或封禁通知。

**缓解措施：**
1. **优先用官方 API**，遵守其 rate limit 与 User-Agent 规范；
2. 尊重 `robots.txt` 与 `Crawl-delay`；
3. 不做全量爬取，只做「按需查询 + 增量同步」；
4. 缓存已获取数据，减少重复请求；
5. 关键数据源准备备选（如 arXiv 不可用时有 Crossref 兜底）；
6. 明确不做：绕过付费墙、抓取需要授权的全文。

**责任人：** DS
**关联任务：** `S3-MS04`、`S3-MS05`、`S3-MS06`

---

### R-C03 · AI 生成内容的学术诚信风险 【H × H】

**描述：** 本系统生成套磁信、综述初稿、伦理声明。若用户直接提交未经核验的 AI 内容，可能构成学术不端。这不只是用户的问题——**提供这样的工具本身就有责任**。

**触发信号：** 试点用户反馈「直接用了生成的综述被导师指出问题」。

**缓解措施：**
1. **证据锚点是核心防御**：所有生成内容必须绑定 `evidence_anchors`，无证据的断言不允许输出（W1 规则）；
2. 生成内容**强制标注**「AI 辅助生成，请核验后使用」；
3. 综述与套磁信定位为「初稿/提纲」，不做「一键成品」的产品暗示；
4. `retract-radar` 站主动做合规检查，包括 AI 使用披露声明生成——这是把风险转化为功能的正面设计；
5. 用户协议明确：生成内容的学术责任由使用者承担，但平台保证不伪造证据。

**责任人：** TL + DS
**关联任务：** `S3-MS07`、`S3-MS14`、`S3-MS15`；W1 规则

---

### R-C04 · 综测加分核算错误的法律/信任风险 【H × H】

**描述：** 综测分数直接影响保研资格。若系统算错分，可能导致学生错失机会，引发严重纠纷与信任崩塌。这是**零容忍**的功能。

**触发信号：** 任一用户反馈加分计算与学校规定不符。

**缓解措施：**
1. **计算准确性是 G4 的一票否决项**：3 所高校各一套规则，30 个构造用例零错误；
2. 所有加分项**必须可追溯到证据**（`asset_node` + `evidence_anchors`），不采信用户手填的孤立数字；
3. UI 明示「本结果为辅助参考，最终以学校认定为准」；
4. 提供**计算过程可展开**：每个分数怎么来的、用了哪条规则、对应哪份材料，全部可见可核；
5. 规则变更留痕（谁在何时改了什么），避免规则被随意调整。

**责任人：** BE2 + TL
**关联任务：** `S4-01`、`S4-02`

---

### R-C05 · 证据锚点失效导致简历/论文引用断链 【M × H】

**描述：** DOI 可能失效、PDF 链接可能变更、GitHub 仓库可能删除。简历中的「可验真证据」若断链，比没有证据更糟——它损害可信度。

**触发信号：** 抽检 50 条简历经历出现断链。

**缓解措施：**
1. 定期（每周）批量校验 `evidence_anchors` 的有效性；
2. 失效时**明确展示失效状态**（灰色 + 「原始来源已不可访问」），不假装有效；
3. 对已获取的 PDF 存快照（对象存储），DOI 失效时仍可展示原始证据；
4. G4 验收要求断链率 0（基于抽检时点）。

**责任人：** BE3
**关联任务：** `S4-03`

---

### R-C06 · 第三方接入的数据边界模糊 【M × M】

**描述：** 第三方实验室站接入后，其收集的数据归谁、是否可被平台方查看、用户是否知情——边界不清会引发合规与信任问题。

**触发信号：** 第三方站上线后出现数据归属争议。

**缓解措施：**
1. manifest 中**强制声明**数据用途与存储位置，hub 在挂载时向用户展示；
2. 第三方站的资产进独立命名空间，平台默认不可读（除非用户显式授权）；
3. 用户可在设置中查看「哪些第三方站在使用我的数据」并可解除授权；
4. 接入协议中明确责任划分。

**责任人：** TL
**关联任务：** `S4-05`、`S4-07`；ADR-08
