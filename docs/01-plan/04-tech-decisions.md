## ADR-01 · Monorepo 工具链选型

**状态：** 提议
**决策者：** Tech Lead
**影响范围：** 全仓库

### Context

需要在一个仓库里管理：18 个 Next.js 应用 + 1 个 hub + 1 个小程序 + 3 个 TS 包 + 3 个 Python 服务 + 契约文件。核心诉求是：
1. 18 个微站共享 `packages/*`，避免 18 倍重复构建；
2. JS 与 Python 都要能纳入统一的任务编排与 CI；
3. 团队 6 人，运维复杂度必须低。

### Decision

**采用 Turborepo + pnpm workspace 管理 JS/TS 部分；Python 服务不进 Turborepo 的包图，用 `uv`（或 poetry）独立管理依赖，但**纳入 Turbo 的 task pipeline 调用**。**

结构：
- `pnpm-workspace.yaml` 声明 `apps/*`、`apps/micro-sites/*`、`packages/*`；
- `turbo.json` 定义 `build` / `lint` / `typecheck` / `test` / `dev` pipeline，并开启 remote cache（Vercel Remote Cache 或自建 S3 cache）；
- Python 服务在 `services/*/` 下各自有 `pyproject.toml`，Turbo 中通过自定义 task 调 `uv run pytest` 等，但**依赖解析不跨语言**；
- `contracts/` 的代码生成是一个 Turbo task，产出物入库。

### Consequences

**正面：**
- Turbo 的 remote cache 对「18 个应用共享少量包」这个形态收益最大：`packages/instrument-ui` 改一次，18 站重建，但缓存让增量构建几乎瞬时。
- 相比 Nx，Turborepo 配置面小得多，6 人团队不需要专人维护工具链。
- pnpm 的严格 node_modules 结构天然阻止「微站偷偷 import 了没声明的依赖」，这与 A1「一站崩不连带」的精神一致。

**负面（必须接受的代价）：**
- **跨语言编排是拼凑的**。Turbo 不真正理解 Python 依赖图，`services/` 之间的依赖关系要靠人维护。若 Python 服务增多（> 5 个），这套方案会变脆。
- Remote cache 需要额外的基础设施或付费（Vercel Remote Cache 免费额度有限）。若用自建 S3 cache，需要有人维护。
- pnpm 的严格性会让不熟悉的成员频繁踩「幽灵依赖」报错，前期有学习成本。
- Turborepo 的 `dev` 并行启动 18 个应用会吃掉大量内存，**必须**提供「只启动我关心的站」的过滤脚本。

**需要在评审时补充的信息：** 团队是否已有 S3/OSS 可用？若无，remote cache 改用本地 cache + CI 缓存。

### Alternatives

| 方案 | 否决原因 |
| :--- | :--- |
| **Nx** | 能力更强（原生支持 Python 插件、更细的任务图），但配置复杂度与学习曲线显著高于 Turbo。6 人团队里没有专职平台工程师时，Nx 的维护成本会侵蚀交付时间。若团队已有 Nx 经验，此项可翻转 |
| **pnpm workspace 裸用（无 Turbo）** | 缺少任务编排与缓存，18 站构建时间线性叠加。在 CI 上会慢到不可接受 |
| **多仓库（每站一仓）** | 与 A1 的「独立部署」看似契合，但会让 `packages/*` 的版本管理变成灾难（18 个仓库各自锁版本）。且契约变更需要 19 个 PR 协同，不可行 |
| **Bazel** | 对纯前端 + 小团队是过度工程，收益不足以抵消复杂度 |

## ADR-02 · 多站点部署策略：子域名 vs 子路径

**状态：** 已由蓝图锁定，此处记录论证
**影响范围：** 全部 18 站 + hub

### Context

蓝图 Q1 已锁定「独立二级域名 `*.matrixos.edu`」。但工程上必须重新审视一次，因为这个决策一旦落地就极难回退（涉及 Cookie 域、CORS、证书、SEO、部署流水线）。

### Decision

**采信蓝图结论：18 个微站各自使用独立子域名 `*.matrixos.edu`。** hub 为 `orbital.matrixos.edu`。

同时确定三项配套约束：
1. **域名是路由的唯一事实源**：`specs/microsites.json` 的 `domain` 字段决定部署路由，目录名不参与路由；
2. **域级 Cookie**：`mx_at` 设 `Domain=.matrixos.edu`，实现一次登录全域生效；
3. **通配符证书**：`*.matrixos.edu` + `matrixos.edu` 双 SAN，避免 18 张证书的运维负担。

### Consequences

**正面：**
- **技术上正确的隔离**：子域是同源策略的天然边界，微站之间的 JS 无法直接访问彼此的 DOM/localStorage。这为 A1 的「一站崩不连带」提供了浏览器级的保障（子路径方案下，一个站的 XSS 可以读另一个站的存储）。
- 独立部署天然契合：每个子域可独立指向不同的部署、独立灰度、独立回滚。
- 第三方实验室插槽（A5）需要给他们一个独立域名；子域模式下追加一条 DNS 记录即可，子路径模式则需要改 hub 的路由表并重新部署 hub。
- 用户心智：`curvelab.matrixos.edu` 比 `matrixos.edu/curvelab` 更像「一个独立产品」，符合「群岛式微站」的产品定位。

**负面（必须接受的代价）：**
- **第三方 Cookie 风险是真实的**。当微站被 iframe 嵌入 hub 时，子域在 iframe 内属于「第三方上下文」，Safari ITP 与 Chrome 的第三方 Cookie 限制会导致 `mx_at` 不被发送。**这是本决策最大的代价**，必须用 ADR-03 的 `mx_idt` 交换机制来兜底，该机制不是优化项而是必做项。
- **证书与 DNS 管理**：18 + N 个子域。用通配符证书 + 泛解析 DNS 可缓解，但第三方接入时（他们用自己的域名或需要新子域）仍需人工介入。已登记为 `BL-05`。
- **SEO 分散**：18 个子域被搜索引擎视为不同站点，权重不聚合。对本项目（校内工具，无 SEO 诉求）影响可忽略，但需明示。
- **CORS 配置维度增加**：任何跨站调用都需要显式配置 allowed origin 列表。这项复杂度被 SDK 收敛（微站不手写 CORS），但服务端仍需维护白名单。

### Alternatives

| 方案 | 否决原因 |
| :--- | :--- |
| **子路径 `matrixos.edu/curvelab`** | 同源，无 Cookie 问题，部署简单（一个 Next.js 多 zone）。但：① 微站之间无浏览器级隔离，一站 XSS 可读全局存储，与 A1 冲突；② 独立部署与独立回滚变得困难（多 zone 需要统一 router）；③ 第三方插槽无法给出独立域名。**若团队规模缩小到 2–3 人且有强运维约束，此方案反而更务实——这是一个真实的权衡点** |
| **每站独立主域名** | 品牌分散且成本高（18 个域名），Cookie 无法共享，SSO 需跨域方案，明确不可行 |
| **单一 SPA 内做路由分区** | 就是蓝图要废除的「42 工具大杂烩单页」，与 Q1 公理直接冲突 |

## ADR-03 · 鉴权方案

**状态：** 提议
**影响范围：** 全部站点 + 服务

### Context

需要同时满足：一次登录 18 站通用（A2）、单站被攻破时损失可控、iframe 嵌入场景可用（A4）、小程序端可接入（双端协同）、第三方实验室站可受限接入（A5）。

### Decision

**MatrixID 作为唯一 IdP，采用 OAuth2 授权码流 + RS256 JWT。**

四类令牌：
| 令牌 | 载体 | 有效期 | 用途 |
| :--- | :--- | :--- | :--- |
| `mx_at` | HttpOnly Cookie，`Domain=.matrixos.edu` | 15 min | 访问 API |
| `mx_rt` | HttpOnly Cookie，路径限定 `/v1/auth` | 30 d 滑动 | 换发 `mx_at`，一次性 + 重放检测 |
| `mx_idt` | 内存，不落盘 | 120 s | iframe 场景一次性交换凭证 |
| `mx_devkey` | 服务端签名密钥 | 90 d | 第三方实验室站 |

**关键机制：iframe 内不依赖 Cookie，改用 `mx_idt` 交换。**
hub 通过 `postMessage` 把 `mx_idt` 交给 iframe 内的微站，微站用它调 `/v1/auth/exchange` 换一次 `mx_at`（存在内存 + sessionStorage，非 Cookie）。这样第三方 Cookie 被阻断也不影响。

**授权粒度：** scope 形如 `station:<site_key>:<verb>`，verb ∈ `read|write|emit`。微站能读写的范围由 JWT 内的 scope 决定，而非"登录了就全都能干"。

### Consequences

**正面：**
- 域级 Cookie 在**非 iframe 场景**（用户直接访问子域）下提供零成本的 SSO。
- `mx_idt` 机制让 iframe 场景在第三方 Cookie 被阻断时仍可用，且 `mx_idt` 一次性 + 120s 短效，泄漏窗口极小。
- scope 细粒度让「某站被攻破」的爆炸半径限制在该站 scope 内，符合安全最小权限原则。
- 第三方站用 `mx_devkey`，与官方站的主令牌体系隔离，便于审计与吊销。

**负面（必须接受的代价）：**
- **双通道复杂度**：非 iframe 走 Cookie、iframe 走 `mx_idt` 交换，等于两套路径。这会产生「在我机器上能登录、在 iframe 里不行」这类难查的问题。缓解：SDK 内部统一封装，开发者只调 `initSSO()`，不感知差异；但**SDK 自身必须对两条路径都有测试**。
- **`Domain=.matrixos.edu` 的 Cookie 是全域共享的**，这意味着任何一个子域上的 XSS 都能读到 `mx_at`。这是域级 Cookie 的固有风险。缓解：HttpOnly 使 JS 无法读 Cookie 值，但 XSS 仍可发起带 Cookie 的请求（CSRF 式）。因此 CSRF 双提交令牌是必需的，不是可选的。
- **`mx_rt` 30 天滑动**意味着长期不活跃用户仍保有 refresh 能力。若设备丢失，风险窗口长达 30 天。缓解：提供「登出所有设备」（`/v1/auth/logout-all` 拉黑 `jti`），并在敏感操作（改密码、导出简历）时要求二次认证。
- **RS256 密钥轮转**需要设计：旧公钥要保留一段时间供验签。这个机制常被遗漏，必须写入实现验收标准。
- **CAS 对接不确定性**：校园 CAS 的协议实现质量参差，可能只支持 SAML 或自定义协议。兜底方案（邮箱 + 密码）会增加一个凭据体系，需额外的安全投入（密码哈希、找回流程）。

### Alternatives

| 方案 | 否决原因 |
| :--- | :--- |
| **纯 Session（服务端 session + Cookie）** | 简单，但 18 站共享 session 需要共享 session store，且跨 iframe 时同样受第三方 Cookie 限制。JWT 的 scope 表达力更强 |
| **纯 OIDC 第三方 IdP（Auth0/Clerk 等）** | 省事，但成本（每 MAU 计费）与本项目「单用户年均 ¥1.5」的极致成本目标冲突，且校园用户数据出境/出校有合规顾虑 |
| **LocalStorage 存 token（不用 Cookie）** | 完全规避第三方 Cookie 问题，但 XSS 可直接窃取 token，风险高于 HttpOnly Cookie。仅在 iframe 路径下用内存/sessionStorage 作为折中 |
| **每个微站独立登录** | 直接违反 A2，用户体验灾难 |

## ADR-04 · 向量库选型

**状态：** 提议
**影响范围：** `matrix-core`、资产检索

### Context

`DigitalTwinAssetGraph` 需要向量检索能力：跨论文语义检索、导师匹配度计算、同类资产推荐。数据规模预估：500 试点用户 × 平均 200 条资产 × 3 切片 ≈ 30 万向量；扩容到 5000 用户约 300 万。

### Decision

**采用 PostgreSQL + pgvector（HNSW 索引），不引入独立向量数据库。**

- `asset_chunk.embedding vector(1024)`，HNSW 索引，`m=16`、`ef_construction=64`；
- 检索在 `matrix-core` 内通过 SQL 完成，不另起服务；
- 向量维度 1024 对应主力 embedding 模型（评审时确认具体模型）。

### Consequences

**正面：**
- **事务一致性**：资产元数据与向量在同一个数据库、同一个事务里写入。这是最关键的理由——如果用独立向量库，会出现「元数据写成功但向量没写」的漂移，而资产图谱恰恰要求两者严格对应。
- **运维面最小**：一个 PostgreSQL 实例同时承担关系数据、JSONB、向量检索。6 人团队不需要维护第二套存储。
- **权限模型统一**：`matrix_uid` 的行级权限在 SQL 里做，若引入外部向量库，就得在应用层重新实现一遍权限过滤（易漏，且是越权高发点）。
- 成本低：pgvector 无额外费用。

**负面（必须接受的代价）：**
- **性能上限明确**：pgvector 在千万级向量上性能会明显落后于专用向量库（Milvus/Qdrant）。按当前预估（300 万），HNSW 单机可承受；但**如果资产规模超出预估 10 倍，这里会成为瓶颈**。需要设定明确的扩容触发阈值（见下）。
- **索引构建占用资源**：HNSW 建索引是内存与 CPU 密集操作，在数据量大时会阻塞写入。缓解：低峰期建索引，或用 `CONCURRENTLY` 相关策略。
- **embedding 维度锁死**：`vector(1024)` 是列定义，换 embedding 模型若维度变化需要迁移。缓解：换模型时新增列而非改原列，双写过渡。
- 复杂向量查询（多向量混合、带过滤的近似检索调优）不如专用库灵活。

**扩容触发条件（写入监控）：** 当 `asset_chunk` 行数 > 500 万，或向量检索 P95 > 500ms 持续一周，则启动「拆分独立向量库」的评估。这不是现在就做，而是预设的决策点。

### Alternatives

| 方案 | 否决原因 |
| :--- | :--- |
| **Qdrant / Milvus 独立向量库** | 性能更强、扩展性更好。但引入双写一致性问题、多一套运维、权限需在应用层重实现。当前数据规模下收益不抵复杂度。**若项目预期用户量远超试点规模，此项应翻转** |
| **Elasticsearch / OpenSearch** | 可同时做全文与向量检索，但资源占用重（JVM），且我们已经用 PG 全文检索（`tsvector`）覆盖了关键词检索需求 |
| **纯内存向量索引（FAISS in-process）** | 无法持久化、无法多实例共享、重启即失效，不适合服务端 |
| **不存向量，实时调用 embedding API** | 每次检索都要重新 embedding 全库，成本与延迟都不可接受 |

## ADR-05 · 端侧隐私仓方案

**状态：** 提议
**影响范围：** `@matrixos/sdk`、全部微站、TIER 04 本地模型

### Context

蓝图要求「本地 IndexedDB 隐私仓已加密」，并承诺 TIER 04 处理「课题组未发表实验原始数据」时「零外泄」。这既是技术需求，也是对用户的**承诺**——承诺不兑现就是欺骗。

### Decision

**端侧 IndexedDB + WebCrypto AES-GCM 加密 + PBKDF2-SHA256（≥ 310,000 迭代）密钥派生。**

- 敏感数据按记录粒度加密，密文 + IV 存 IDB；
- 密钥由用户 passphrase 派生，**仅存内存与会话**，不落 Cookie、不上传服务端；
- 非敏感数据（已发表论文元数据）明文存服务端，跨设备可用；
- 原始实验数据**只在端侧**，服务端只存 `local_ref` 指针。

### Consequences

**正面：**
- 服务端被拖库也无法解密端侧数据，「零外泄」在技术上成立（而非仅靠政策承诺）。
- PBKDF2-SHA256 310k 迭代是 OWASP 当前推荐值，抗暴力破解能力足够。
- AES-GCM 提供认证加密，密文被篡改会被检测到。

**负面（必须接受的代价）：**
- **密钥丢失即数据永久不可恢复**。用户忘记 passphrase，未发表的实验数据就没了。这是无法用技术解决的取舍，只能靠 UI 反复警告 + 提供「导出加密备份」的补救路径。**必须写入用户协议**（已登记 `05-risks.md` R-14）。
- **无法跨设备访问原始数据**。用户在实验室电脑做的拟合，回家打不开原始数据。这是物理隔离的必然结果。产品上必须诚实展示「原始数据在设备 X」而不是报错（见 `S2-15`）。
- **PBKDF2 在低端设备上耗时明显**（310k 迭代可能 200–500ms）。冷启动时若需解锁隐私仓，会影响 800ms 冷启动目标。缓解：非必要不自动解锁，改为首次访问隐私数据时按需解锁。
- **WebCrypto 在非安全上下文（HTTP）不可用**。开发环境必须用 HTTPS 或 localhost。这会增加本地开发的摩擦。
- **IndexedDB 有容量限制且可能被浏览器清理**。Safari 对未被频繁访问的站点会清理 IDB。需要提供「数据导出」作为兜底，并检测清理事件提示用户。

### Alternatives

| 方案 | 否决原因 |
| :--- | :--- |
| **服务端加密存储（服务端持密钥）** | 实现简单、可跨设备，但违背「零外泄」承诺（服务端能解密）。且一旦服务端被攻破/内部人员滥用，数据全失 |
| **E2E 加密 + 密钥托管（用户密钥加密后存服务端）** | 可跨设备，安全性优于纯服务端加密。但复杂度高（密钥同步、恢复流程），且仍需要一个「可信的密钥托管」——本质是把问题转移。**若跨设备是硬需求，这是正确的方向，已登记为 `BL-04`** |
| **不加密，仅靠浏览器同源隔离** | IDB 是明文，任何 XSS 或设备访问都能读取。不满足「未发表数据」的敏感度要求 |
| **本地文件系统（File System Access API）** | 用户可感知、可备份，但浏览器支持不一致（Safari 不支持），且体验割裂 |

## ADR-06 · 模型分级路由

**状态：** 提议
**影响范围：** `copilot-router`、全部 AI 功能

### Context

蓝图给出四级模型矩阵与「单用户年均 API 成本 < ¥1.5」的硬指标。需要在保证体验的前提下把成本压到这个数量级。¥1.5/年 意味着平均每用户全年只能花 1.5 元——按 Pro ¥2/百万 token 算，约 75 万 token/年 ≈ 2000 token/天，非常紧张。

### Decision

**四级路由 + 三级成本控制。**

路由层：
```
意图/早报        → DeepSeek V4.1 Flash  (¥0.30/M)
schema 校验/自愈 → Qwen 3.8 Flash       (¥0.40/M)
长文本攻坚       → DeepSeek V4 Pro      (¥2.00/M)
隐私/术语校准    → 本地 Qwen 3.8-7B LoRA (¥0)
```

成本控制三层：
1. **路由准确率**：意图分类错误会让 Pro 被滥用。目标 ≥ 95%，用 200 条标注集守护。
2. **成本熔断**：按 `matrix_uid` 记日成本，超阈值自动降级到 Flash 并记录降级事件。
3. **结果缓存**：相同/相似请求（如多用户查询同一篇论文的摘要）命中缓存不重复计费。

### Consequences

**正面：**
- 分级让 90%+ 的请求走 Flash 档，Pro 只用于真正需要长上下文的场景，成本结构合理。
- 成本熔断是**兜底保险**：即使路由判断失误，单用户成本也不会失控。
- 缓存对「热门论文/热门导师」场景效果显著（试点校同专业学生查询高度重叠）。
- 本地 LoRA 处理隐私数据，既不花钱又满足零外泄。

**负面（必须接受的代价）：**
- **路由判断本身要花 token**。意图分类也是一次 LLM 调用，虽然用最便宜的 Flash，但如果每次用户输入都先分类，成本会显著累积。缓解：用规则/关键词优先做初筛，只有模糊输入才调模型分类。
- **降级会伤害体验**。用户被熔断后，长文本对比任务质量下降，可能引发投诉。必须让用户可见（「已切换至经济模式」），而不是静默降级。
- **¥1.5/年 的目标很激进**。真实用户行为可能集中在 Pro 类任务（比如反复做长文本对比）。如果实测超标，只能靠：① 更激进的结果缓存；② 提高 Pro 的使用门槛（如每日配额）；③ 重新谈成本目标。**这一点必须在 S2 的回放测试中验证，不能假设能达标。**
- **本地 LoRA 的可达性**：需要校内 GPU 资源常驻。若无，隐私任务只能降级到「不上传，仅本地规则处理」，功能受限。
- **多供应商维护成本**：DeepSeek 与 Qwen 的 API 差异（错误码、限流策略、并发限制）需要适配层吸收。

### Alternatives

| 方案 | 否决原因 |
| :--- | :--- |
| **全部用 Pro** | 质量最好，但成本会超标数量级，直接违反硬指标 |
| **全部用 Flash** | 成本最低，但长文本对比、综述生成的质量不可接受，核心价值受损 |
| **自建开源模型全量替代** | 省 token 费，但需要大量 GPU 与推理运维，且通用能力远不及商业模型。仅在「隐私数据」这一窄场景用本地模型是合理折中 |
| **按订阅等级分级（免费用户 Flash、付费用户 Pro）** | 商业上合理，但 v3 无订阅体系（BL-03），且会产生「付费才有好体验」的负面感知 |

## ADR-07 · UI 组件库方案

**状态：** 提议
**影响范围：** `packages/instrument-ui`、全部微站

### Context

蓝图要求「数字精密科研仪器」视觉体系：阻尼旋钮、荧光示波器、极坐标声呐盘、激光连线表格。这类组件与常规后台组件库（表格、表单、弹窗）完全不同，通用库无法直接满足。

### Decision

**分层：底层用 shadcn/ui（Radix primitives + Tailwind），在其上自建 `instrument-ui` 仪器组件库。**

- 通用交互（对话框、下拉、Tooltip、焦点管理、无障碍）用 Radix primitives，不自己造；
- 仪器专属组件（旋钮、示波器、声呐盘、证据连线表）自建，且**必须**是受控组件（props in / events out，无内部数据获取）；
- 设计 token 统一从蓝图提取：`obsidian #050814`、`panel #0B1021`、brand 六色（indigo `#6366f1`、cyan `#06b6d4`、emerald `#10b981`、amber `#f59e0b`、rose `#f43f5e`、violet `#8b5cf6`）；
- 组件文档用 Storybook，每个仪器组件必须有正/负两种状态示例。

### Consequences

**正面：**
- 不重复造无障碍/焦点管理的轮子——这是自建组件库最容易翻车的地方，Radix 已经解决。
- Tailwind 让 18 个微站共享设计 token 时无需引入 CSS-in-JS 运行时。
- 仪器组件受控化后，可以在 hub 与独立微站两种上下文复用，数据来源由外部注入。这是 A4 双态复用的前提。

**负面（必须接受的代价）：**
- **仪器组件的工作量被严重低估的风险**。Canvas 示波器要支持 1 万点 30fps 重绘、置信带、残差叠加，这不是「画条线」那么简单。`S3-02` 估 15 pd 可能偏乐观。
- **shadcn/ui 是「复制粘贴」模式而非依赖包**，组件代码进仓库。好处是可深度定制，坏处是无法通过升级包获得修复，需要自己跟上游变更。
- **Canvas 组件难以做无障碍**。示波器、声呐盘对屏幕阅读器不友好。缓解：提供等价的数据表格视图（不能只有图形）。
- 自建组件库天然有「建了没人用」的风险。已在 G3 验收中强制「每族 ≥ 2 个组件被 ≥ 2 站复用」。
- 仪器视觉（微拟物、荧光、光晕）在低端设备上可能掉帧，需要降级方案（如低性能设备关闭光晕）。

### Alternatives

| 方案 | 否决原因 |
| :--- | :--- |
| **Ant Design / MUI 全量** | 常规后台组件覆盖好，但「精密仪器」视觉完全无法实现，会被其设计语言绑死 |
| **纯自建（不用 Radix）** | 无障碍、焦点陷阱、键盘导航全部要自己实现，是巨大的时间黑洞且容易做错 |
| **纯 Headless UI + 完全自定义** | 与 shadcn/ui 思路类似但生态更小，Radix 的 primitives 质量更高 |
| **引入 ECharts / D3 做仪器图** | 对标准图表合适，但「阻尼旋钮调节参量实时重绘 + 置信带 + 残差」这类交互，图表库的抽象反而成为束缚。可考虑局部使用 D3 做比例尺与曲线插值，但组件外壳自建 |

## ADR-08 · 微前端插槽机制

**状态：** 提议
**影响范围：** `orbital-hub`、`@matrixos/sdk`、第三方接入

### Context

hub 要在右 68% 区域同屏挂载 2–3 个微站（A4），且要支持第三方实验室站热插拔（A5），同时 18 个站技术栈必须统一（都是 Next.js）。这是个「微前端」问题，但比典型微前端简单——所有官方微站同构。

### Decision

**采用 iframe + `postMessage` 的「重隔离」方案，不引入 Module Federation / qiankun 等运行时方案。**

- 每个微站是独立部署的完整应用，hub 用 `<iframe>` 挂载；
- 跨边界通信统一走 `@matrixos/sdk` 的 `useHostBridge()`，封装 `postMessage` 的握手、版本协商、origin 校验；
- 第三方实验室站同样用 iframe，**这是唯一能让第三方代码安全接入的方式**；
- 官方微站必须支持「iframe 内降级模式」（隐藏自身导航，适配紧凑布局）。

### Consequences

**正面：**
- **隔离最强**：iframe 提供完整的 JS/CSS 隔离。第三方实验室的代码再烂，也不会污染 hub 或其他微站。这对 A5 开放生态是决定性的——你不可能让不可信的第三方代码和主应用共享 JS 上下文。
- **技术栈无关**：虽然官方站都是 Next.js，但第三方站可以用任何框架。iframe 不关心。
- **实现最简单**：不需要处理样式冲突、依赖版本冲突、共享状态管理。这三种问题是 Module Federation 方案的主要痛点。
- 天然支持独立部署与独立回滚（A1）。

**负面（必须接受的代价）：**
- **性能代价是真实的**：3 个 iframe = 3 份 React 运行时 + 3 份 SDK + 3 个独立的 hydration 过程。内存与主线程压力显著。`S2-01e` 的性能探针就是为此设的。**如果探针显示不可接受，降级方案是「1 个全量 iframe + 2 个静态快照缩略图」**——视觉上仍是「同屏挂载 3 台仪器」，但只有 1 台是真活的。这是一个真实的产品妥协。
- **iframe 通信是异步的且慢**。`postMessage` 的序列化开销让「拖动数据卡片跨 iframe」这类高频交互变顿挫。缓解：拖拽过程中的视觉反馈全部在 hub 层完成（环体、拖影），只在松手瞬间发一次消息。
- **布局与滚动耦合**：iframe 的高度自适应需要反复测量，容易出现双滚动条。必须统一约定 iframe 内不滚、由 hub 控制外层滚动。
- **调试体验差**：跨 iframe 的 bug 需要在多个 DevTools 上下文间切换。
- **第三方 Cookie 问题**（见 ADR-02/03）：iframe 内鉴权必须走 `mx_idt` 交换。

### Alternatives

| 方案 | 否决原因 |
| :--- | :--- |
| **Module Federation（Webpack 5 / Rspack）** | 共享运行时、通信高效、体验最接近单页应用。但：① 要求所有微站构建工具与共享依赖版本严格对齐，第三方站几乎不可能满足；② 样式与全局状态污染风险高；③ 对第三方代码没有安全隔离。**对「官方 18 站」是更优解，对「开放生态」是不可行解** |
| **qiankun / micro-app** | 本质是 JS 沙箱 + 样式隔离，隔离强度弱于 iframe，且同样要求技术栈可控。对第三方不可信代码不足够 |
| **Web Components** | 样式隔离好（Shadow DOM），但 JS 仍共享上下文，无安全边界；且跨框架的 props/events 传递繁琐 |
| **直接内嵌组件（npm 依赖，非运行时挂载）** | 等于把 18 站打成一个巨型应用，直接违反 A1，且第三方无法接入 |

> **一个重要的补充判断：** 如果本项目**放弃第三方生态**（A5 不做），那么 Module Federation 是明显更优的技术选择。选择 iframe 的根本原因是**为了换取开放插槽的安全边界**。这个因果关系必须在评审时明确——如果 A5 被砍，ADR-08 应当推翻重做。

## ADR-09 · 错误处理与降级策略

**状态：** 提议
**决策者：** Tech Lead + BE2
**影响范围：** 全部服务与站点

### Context

规划中发现一个未被讨论但影响面极大的决策：当核心服务（`matrix-core`）不可用时，18 个微站应该有怎样的行为？由于架构上 `matrix-core` 是所有站点的共同依赖，它一旦挂掉，理论上全站瘫痪——这与 A1「一站崩不连带」的精神直接矛盾（微站独立了，但共享依赖还是单点）。

### Decision

**三层降级，按可用性优先级：**

| 层级 | 触发条件 | 行为 |
| :--- | :--- | :--- |
| L0 正常 | `matrix-core` 健康 | 全功能 |
| L1 鉴权降级 | `/v1/auth` 超时但资产 API 正常 | 用未过期的 `mx_at` 继续；超过 15min 未刷新则展示「登录即将过期」并重试 |
| L2 只读离线 | `matrix-core` 整体不可用 | 微站从 IndexedDB 读缓存，展示已有数据，**明确标注「离线模式，数据可能不是最新」**，禁止写入 |
| L3 静态兜底 | 微站自身构建/部署故障 | 展示静态维护页，hub 星轨中该站胶囊置灰并标注「维护中」 |

**强制要求：**
1. SDK 内置熔断器（连续 3 次失败后短路 30s，指数退避），微站不自己实现；
2. L2 状态必须在 UI 上**显式可见**，不允许静默降级（用户看到旧数据却不知道）；
3. hub 必须能感知各微站健康状态（心跳接口），并在星轨上体现（正常/降级/维护三态）。

### Consequences

**正面：**
- 让「微站独立」在依赖故障时仍然有意义：至少用户能看历史数据，而不是白屏。
- 显式降级标注避免「用户基于过期数据做决策」的风险。
- 熔断器收敛在 SDK 里，18 站不会各自实现出 18 种行为。

**负面（必须接受的代价）：**
- 每个微站都要实现「离线读缓存」路径，这是**额外工作量**，且容易做漏（`S2-16` 是 P1 而非 P0，说明我判断它在 S2 可以降级——但如果降级，L2 兜底就只剩白屏）。
- 缓存一致性是难题：离线时读到的数据可能与服务端冲突，恢复后需要合并策略。当前方案是「离线只读、不写」，规避了冲突合并，但也意味着离线时用户什么都做不了。
- 熔断器参数（3 次/30s）是拍的，可能需要按实际故障模式调整。
- 微站健康心跳增加 hub 的复杂度与请求量。

### Alternatives

| 方案 | 否决原因 |
| :--- | :--- |
| **不做降级，直接白屏** | 最简单，但用户体验灾难。而且 `matrix-core` 一挂全站白屏，会让「群岛式架构」的独立性成为一个笑话 |
| **每个微站自带本地数据库（各自独立 PG）** | 真正消除单点，但直接违反 A2（统一资产底座），且 18 个数据库的运维成本不可接受 |
| **多活部署 `matrix-core`** | 解决的是可用性而非降级体验，且成本高。可作为 L2 之上的补充，但不能替代降级设计 |

## ADR-10 · 契约演进与版本策略

**状态：** 提议
**决策者：** Tech Lead
**影响范围：** `contracts/`、全部服务与站点

### Context

Wormhole envelope 与 manifest 是 18 站 + 第三方站的共同依赖。一旦上线，任何字段语义变更都会引发多方返工。规划中 `S1-04` 只解决了「漂移检测」，没解决「如何演进」。

### Decision

**语义化版本 + 向后兼容优先 + 双写过渡期。**

- `contracts/` 中每个 schema 有明确 `$id` 含版本号（如 `wormhole-envelope.v1.schema.json`）；
- **只增不改**：v1 内只允许新增可选字段，禁止修改/删除已有字段语义；
- 破坏性变更 → 发布 v2，服务端**同时**支持 v1 与 v2 至少一个阶段（双写/双读），微站按自己的节奏迁移；
- manifest 中的 `accepts` 声明包含版本：`accepts: ["curve_fit_parameters:v1"]`；
- 目标站收到不支持的版本 → 明确报错「该站暂不支持 v2 载荷」，而非静默丢弃。

### Consequences

**正面：**
- 18 站可以不同步升级，这是现实约束（不可能要求 18 个站同一时刻上线）。
- 第三方站有明确的兼容承诺，敢于接入。
- 双写期内新老共存，避免「一刀切」导致的全站故障。

**负面（必须接受的代价）：**
- 双写期增加实现复杂度与测试矩阵（v1 × v2 的组合）。
- 版本累积会造成「历史包袱」：v1 迟迟无法下线，因为总有站没迁移。需要明确的废弃时间表与强制迁移机制。
- 「只增不改」在早期设计不周时会很痛苦——如果 v1 的某个字段设计有缺陷，只能靠新增字段弥补，字段会越来越多。

### Alternatives

| 方案 | 否决原因 |
| :--- | :--- |
| **不版本化，所有站同步升级** | 18 站 + 第三方不可能同步，一次契约变更就会导致全站停摆 |
| **GraphQL 风格的渐进演化** | 思想一致（避免破坏性变更），但本项目契约是消息 envelope 而非查询接口，GraphQL 不适用 |

## ADR-11 · 测试策略

**状态：** 提议
**决策者：** Tech Lead
**影响范围：** 全仓库

### Context

18 个微站 + 3 个服务 + 跨站虫洞 + SSO，测试矩阵巨大。6 人团队不可能对 18 站都做完整的单元 + 集成 + E2E 覆盖。必须有取舍。

### Decision

**按「共享程度」而非「代码量」分配测试投入。**

| 层 | 覆盖要求 | 理由 |
| :--- | :--- | :--- |
| `packages/matrix-sdk` / `twin-schema` | 单测 ≥ 90% | 18 站共用，一个 bug 炸 18 处。这是全仓最该严的地方 |
| `services/matrix-core` | 单测 ≥ 80% + 集成测试 | 鉴权与资产是核心，越权测试必须全覆盖 |
| `services/copilot-router` | 单测 ≥ 70% + 路由准确率评测集 | 路由错了直接烧钱 |
| `packages/instrument-ui` | 单测 ≥ 60% + Storybook 视觉快照 | 组件视觉回归 |
| 18 个微站 | **E2E 冒烟（每站 1 条主链路）+ 不做高覆盖单测** | 微站逻辑相对独立，站内单测的性价比低于 E2E 冒烟 |
| 跨站场景 | 专项 E2E：SSO、虫洞、插槽、降级 | 这是最容易出错也最难查的地方 |

**强制：** 虫洞与 SSO 的 E2E **必须包含负例**（无证据锚点被拒、非法 `mx_idt` 被拒）。只测正例等于没测。

### Consequences

**正面：**
- 测试投入集中在共享层，符合「bug 影响面 × 测试成本」的最优解。
- 微站用 E2E 冒烟代替高覆盖单测，让 18 站的测试成本可控。
- 负例测试覆盖了安全与契约约束的实际执行情况。

**负面（必须接受的代价）：**
- 微站内部逻辑（如拟合算法、综测计算）缺少单测保护。**例外：综测计算必须有单测**（`S4-01` 的 30 个用例是硬要求），因为算错钱是零容忍的。
- E2E 天然 flake 风险高，18 站 × 多条用例的维护成本不低。已在 `S4-12` 要求「连续 10 次无 flake」。
- Storybook 快照的维护成本会随组件增多而上升，容易出现「一改就全红，直接跳过」的恶性循环。

### Alternatives

| 方案 | 否决原因 |
| :--- | :--- |
| **统一要求高覆盖** | 6 人团队做不到，强推的结果是写一堆凑数字的假测试 |
| **只做 E2E，不做单测** | 反馈太慢，且共享层的边界条件靠 E2E 覆盖成本极高 |
| **不做测试，靠人工验收** | 18 站 × 4 阶段的回归完全靠人力不现实 |

## ADR-12 · 成本与资源的工程约束

**状态：** 提议
**决策者：** Tech Lead + 项目负责人
**影响范围：** 全部

### Context

`05-risks.md` 与蓝图财务表暴露一个矛盾：蓝图按「500 名种子用户、年支出 ¥38,600、第 9 个月现金流转正」测算，但工程侧的 Reality 是：
- 18 个独立部署（即使 Serverless）有基础成本；
- PostgreSQL + 向量检索 + 对象存储有固定成本；
- 校内 GPU（LoRA 推理）需要资源审批，不一定是免费的；
- 虫洞、早报、OpenAlex 抓取的流量成本真实存在。

### Decision

**设定工程侧的成本红线与优先级：**

1. **基础设施成本红线：¥800/月**（不含模型 API）。超出必须在月度复盘中解释。
2. **成本优先级（从高到低）**：可用性 > 数据安全 > 用户体验 > 成本。**即：不为省钱牺牲前三项**，但也不允许「反正不贵就随便加服务」。
3. **明确的省法**：
   - 18 站用同一套 Serverless/容器模板，共享构建缓存；
   - 非活跃微站冷启动（不常驻实例）；
   - 向量检索与主库同实例（ADR-04）；
   - 早报等批处理任务用队列削峰。
4. **明确的不能省**：备份（PG 每日全量 + WAL）、监控告警、HTTPS 证书。

### Consequences

**正面：**
- 给出可核算的红线，避免「先做再算账」导致的预算失控。
- 成本优先级的排序让团队在具体取舍时有依据（例如：不会为了省 CDN 费用而牺牲 LCP）。

**负面（必须接受的代价）：**
- ¥800/月 是估算，**未经真实部署验证**。18 个独立部署 + 数据库 + 对象存储，在云厂商上的实际价格可能显著高于此。**这个数字必须在 S1 部署完成后复核并修正**（列为 S1-22 的一部分）。
- 冷启动策略与「hub 首屏 LCP < 2.5s」直接冲突：冷启动延迟可能让某个微站首次挂载要 3–5 秒。需要在体验与成本间反复调。
- 备份与监控是纯成本无收入，容易被首先砍掉，但它们的缺失会在事故时以更大代价偿还。因此写进「不能省」。

### Alternatives

| 方案 | 否决原因 |
| :--- | :--- |
| **不设红线，按需支出** | 高校项目经费有限，失控风险高 |
| **极致省成本（单实例合并部署）** | 会让 18 站退化为单体，违反 A1，且单点故障风险高 |
| **先不计成本，后期优化** | 后期优化的空间往往被架构锁死，成本应在设计期就纳入 |
